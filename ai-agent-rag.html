1. Why：为什么需要 RAG

1.1 RAG vs Fine-tuning

维度 微调（Fine-tuning） RAG（检索增强）
幻觉控制 依然严重（模型会强行拟合新旧知识） 显著降低（强制基于事实检索）
实时性 慢（每次更新知识都得重新训练） 即时生效（知识库随时增删改，立刻生效）
可解释性 黑盒（你不知道模型为什么这么答） 白盒（答案有明确的检索来源，可溯源）
成本 极高（需要昂贵的GPU集群和大量标注数据） 极低（只需向量数据库和存储空间）

1.2 RAG vs Fine-tuning 选型

  • 第一问：知识需要实时更新吗？（如：新闻、股价、最新政策）
    • ✅ 是 → 选 RAG（微调无法实时更新，改一次花几万块）。
    • ❌ 否（知识是相对固定的）→ 进入第二问。
  • 第二问：模型需要学习特定的“行话”或“格式”吗？（如：法律文书格式、公司内部术语、特定角色的语气）
    • ✅ 是（强调行为/风格） → 选 微调（RAG擅长查事实，但不擅长改变模型的表达习惯）。
    • ❌ 否（只查事实） → 进入第三问。
  • 第三问：你能接受模型因为信息不足而“编造”吗？或者答案必须附上原文出处吗？
    • ✅ 不能接受，必须有据可查 → 选 RAG（微调是黑盒，无法溯源）。
    • ❌ 可以接受（比如写小说、闲聊）→ 进入第四问。
  • 第四问：你的数据量级和预算如何？
    • 数据少（几百条）、预算足 → 选 微调。
    • 数据海量（数十万页）、预算有限 → 选 RAG（微调海量数据极易失败且昂贵）。
  • 如果你的痛点在于“模型答不上来”（缺事实）→ 毫不犹豫选 RAG。
  • 如果你的痛点在于“模型答得不像人话”（缺风格/格式/逻辑）→ 考虑微调。
  • 如果你负责的是核心业务上线 → 先用RAG快速落地（低成本见效），后续数据多了再考虑微调来优化体验（两者结合）。

2. What：RAG 的基本流程

2.1 离线链路：建库

文档 → 切分 → embedding → 入库

目标是把知识准备好。

2.2 在线链路：问答

问题 → 检索 → 重排 → 拼上下文 → 生成

目标是根据用户问题找到资料，并让模型基于资料回答。

RAG 最关键的不是最后生成，而是：

能不能检索到正确、完整、低噪声的上下文。

3. How：RAG 工程关键点

3.1 分块策略

3.1.1 为什么分块如此重要

分块策略的核心，在于平衡 “上下文”与“精确性”。

  • 块太小：每个向量只代表一个思想片段，缺乏回答所需的上下文，答案可能分散在多个块中。
  • 块太大：一个向量包含多个主题，相似度会被稀释，无关信息会挤占宝贵的上下文窗口。

目前主要有以下几种分块策略。

3.1.2 常见分块策略

策略 核心思想 优点 缺点 适用场景
固定大小分块 按固定的Token或字符数切割，可设置重叠部分。 实现简单，速度快，可预测存储和成本。 可能切断句子或语义，缺乏语义连贯性。 快速原型验证，处理结构简单的纯文本文档。
递归字符文本分割 按层级分隔符（如段落、句子）递归切割，尽量保持段落和句子的完整。 比固定大小分块更能保持文本的自然结构。 依赖文档本身的结构，处理不当仍可能切断语义。 通用文本的默认起点，如博客文章、新闻报道。
句子级分块 利用NLP工具按句子边界切割，再合并N个句子为一个块。 块内句子完整，连贯性较好。 句子块通常较短（50-100 Token），可能丢失跨句子的上下文。 问答型文档、客服对话等句子相对独立的场景。
语义分块 先嵌入句子，再根据语义相似度将语义相近的句子合并成块。 块内语义高度连贯，检索精度高。 计算成本较高，速度较慢。 技术文档、研究论文等对检索精度要求高的场景。
上下文感知/父子分块 将文档按层级拆分（如父块是段落，子块是句子），检索子块，但返回其父块以获得更丰富的上下文。 兼顾了检索的精确性和生成时上下文的丰富性。 实现复杂，存储和检索逻辑需要额外设计。 文档结构清晰，需要处理长上下文依赖的场景。

3.1.3 实战建议：如何选择与调优？

  1. 从默认开始：对于大多数RAG应用，递归字符文本分割是一个稳健的默认选择。
  2. 设置初始参数：从中等大小的块（约512个Token） 和 10%-20%的重叠（Overlap） 开始。重叠可以防止关键信息在切割边界被切断。
  3. 用评估来验证：不要凭直觉决定分块大小。分块策略的最终效果，必须通过下一部分要讲的评估指标（如上下文召回率） 来验证。

3.2 Query Transform

3.2.1 Query Transform 的负责者

负责者 适合场景
LLM 复杂问题、多轮对话、拆解、改写、路由
规则 时间、类型、权限、字段过滤
NLP/搜索模块 关键词、实体、拼写纠错、同义词扩展
Agent Planner 多步任务、自主检索、反思重试

3.2.2 Query Transform 的问题分类

类别 解决的问题 包含方法
说清楚 用户问得含糊、口语、省略 Query Rewrite、Follow-up Condense、Query Normalization、Intent Detection
说完整 用户问题太短，关键词不够 Query Expansion、Keyword Extraction、Entity Extraction
拆开问 用户问题太复杂，一次搜不准 Query Decomposition、Sub-question Generation
换角度搜 一个问法搜不到，换多种表达 Multi-query、HyDE、Step-back Query、Hypothetical Question
搜对地方 知识库很多，或需要条件过滤 Query Routing、Metadata Filter Construction

3.2.3 Query Transform 方法表

方法 作用 示例
Query Rewrite 改写问题 “它怎么收费？” → “OpenAI API 如何计费？”
Query Expansion 扩写关键词 “RAG 评估” → “RAG recall@k faithfulness hallucination”
Query Decomposition 拆解问题 “比较 RAG 和微调并说明场景” → “RAG 是什么？”、“微调是什么？”、“二者适用场景？”
Multi-query 生成多个问法 “DPO 是什么？” → “DPO 原理”、“DPO loss”、“DPO 和 PPO 区别”
HyDE 生成假设答案再检索 先让 LLM 写一个可能答案，用答案 embedding 去搜
Step-back Query 抽象成上位问题 “DPO loss 怎么推导？” → “偏好优化的目标函数是什么？”
Follow-up Condense 多轮问题补全 “那它呢？” → “GRPO 相比 PPO 有什么优势？”
Entity Extraction 抽取实体 “小米老板是谁？” → 实体：小米、老板、雷军
Keyword Extraction 抽取关键词 “RAG 为什么会幻觉？” → RAG、幻觉、检索错误、上下文不忠实
Intent Detection 判断意图 “怎么配？” → 是问价格、配置、安装还是参数？
Metadata Filter Construction 构造过滤条件 “找 2024 年的 PPO 论文” → year=2024, topic=PPO
Query Routing 路由到不同知识库 “报销流程” → HR/财务库；“API 报错” → 技术文档库
Hypothetical Question 文档生成可能被问的问题 给文档生成 FAQ，用问题去匹配用户 query
Sub-question Generation 生成子问题 “如何搭建 RAG 系统？” → 文档切分、embedding、向量库、rerank、生成
Query Normalization 标准化表达 “咋弄向量库？” → “如何构建向量数据库？”

3.3 RAG 评估

3.3.1 核心评估框架：RAGAS

RAGAS (Retrieval Augmented Generation Assessment) 是目前最流行的RAG评估框架之一。它的特点是无需参考答案（Reference-Free），可以直接用LLM来评估你的RAG系统输出。它提供了四个核心指标：

指标 衡量什么？ 为什么重要？ 如何计算（逻辑）
Faithfulness (忠实性) 生成的答案是否严格基于检索到的上下文，有无“幻觉”。 确保答案可信、可溯源，减少模型“胡说八道”。 将答案拆解为多个陈述，逐一检查是否被上下文支持。
Answer Relevancy (答案相关性) 生成的答案是否直接、完整地回答了用户的问题。 避免答非所问。一个忠实但跑题的答案依然是无用的。 让评估LLM根据答案反推可能的问题，再与原问题比较相似度。
Context Recall (上下文召回率) 检索到的文档块是否包含了回答问题的所有必要信息。 衡量检索系统查全的能力，避免遗漏关键信息。 将标准答案（Ground Truth）拆解为多个陈述，检查每个陈述是否能在检索到的上下文中找到。Recall = 能被检索文档支撑的黄金事实数 / 黄金事实总数
Context Precision (上下文精确率) 检索到的文档块中，有多少是真正相关的。 衡量检索系统去噪的能力，避免引入无关信息。 评估每个检索到的块与问题的相关性，排名靠前的块权重更高。

3.3.2 其他评估指标与框架

  • 其他重要指标：除了RAGAS的四项核心指标，还有衡量答案准确性的 Answer Accuracy、衡量模型对噪声敏感度的 Noise Sensitivity等。
  • 其他评估框架：DeepEval 和 AgentEval 等也是常用的RAG评估框架。

3.3.3 RAG 评估工作流程

一个标准的RAG评估流程如下：

  1. 准备测试数据集：准备一个包含 “问题” 和 “标准答案（Ground Truth）” 的测试集。
  2. 运行RAG系统：用你的RAG系统处理测试集中的每个问题，记录下 “检索到的上下文” 和 “生成的答案”。
  3. 计算评估指标：使用RAGAS等框架，计算前面提到的各项指标。
  4. 分析结果与迭代：根据指标得分，定位薄弱环节（如Context Recall低，说明检索查不全），然后针对性优化（如调整分块策略、嵌入模型等），再重复评估过程。

4. Agentic RAG

Agentic RAG 是传统 RAG 的进化形态。它通过引入具备自主决策能力的 AI 智能体（Agent），将原本固定、线性的“检索-生成”流程，升级为动态、循环的“规划-检索-评估-再检索”推理工作流。

4.1 传统 RAG vs Agentic RAG

维度 传统 RAG Agentic RAG
工作方式 固定、线性的“检索-生成”流水线 动态、循环的“规划-执行-评估”推理循环
检索策略 单次检索，一次定胜负 多轮迭代检索，可根据需要多次检索并优化策略
决策能力 无，完全按照预设流程执行 有，自主决定查什么、怎么查、何时停止
工具使用 通常仅查询单一的向量数据库 可动态调用多种工具，如搜索引擎、SQL、API 等
错误恢复 无，检索失败则答案质量无法保证 有，可自我评估、优化查询并重试
典型延迟 较低（200-500ms） 较高（1-3秒或更多）
Token 消耗 较低 较高

4.2 实现 Agentic RAG 的主流框架

目前，构建 Agentic RAG 应用主要依赖于以下成熟的智能体框架：

  • LangChain / LangGraph：LangChain 是最流行的 LLM 应用开发框架之一，而 LangGraph 是其扩展，专门用于构建有状态、多步骤的复杂智能体系统。
  • LlamaIndex：一个数据框架，专注于高级文档索引和检索，同样提供了构建智能体工作流的能力
