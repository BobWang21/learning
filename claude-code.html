一句话总览

Claude Code 是一个运行在终端、IDE、桌面端、网页和自动化环境中的 agentic coding assistant。它的核心不是"补全代码"，而是围绕 Claude 模型构建了一个能读项目、搜索、编辑、执行命令、验证结果、管理上下文和接入外部工具的代理运行时。

Claude Code 的设计原则

以下原则不是 Claude Code 功能列表，而是从它的设计中抽象出的 agent 系统目标。一个新的 agent 如果想从演示走向生产，不只是要“更聪明”，还要做到高可用、低成本、安全确定。

抽象原则 核心目标 对新 agent 的启发
高可用 长任务可持续推进，失败后能恢复，结果可验证 让 agent 形成“计划、行动、观察、修正、验证”的闭环
低成本 快速响应，控制 token、延迟和计算开销 默认上下文轻量化，能力按需加载，重复信息可缓存
安全确定 能行动但不失控，关键规则由系统强制执行 把权限、审批、沙箱、回滚和审计放在 harness 层，而不是只靠 prompt

1. 高可用

高可用意味着 agent 不能只在理想路径上工作，还要能处理长任务、路径错误、工具失败、上下文变长和中途恢复。Claude Code 的价值不只是生成答案，而是持续推进任务直到有可验证结果。

🔄 行动闭环

围绕“理解 → 计划 → 行动 → 观察 → 修正 → 验证”设计，让每次工具结果都能成为下一轮决策的输入。

🧭 显式任务状态

用 todo、计划、检查点记录任务进展，避免长任务中遗忘目标，也方便用户理解 agent 当前在做什么。

✅ 结果可验证

运行测试、检查类型错误、查看 diff、读取日志和命令输出，用证据证明任务是否完成，而不是只给文字承诺。

🔁 失败可恢复

路径错误、命令失败、测试失败都不是终点，而是反馈信号；agent 应能调整策略继续推进。

🧩 模型与 harness 分工

模型负责理解、规划、判断；harness 负责执行工具、保存状态、收集结果和维持生命周期。

🧱 能力可扩展

tools、skills、MCP、hooks、subagents、plugins 让 agent 可以接入新工具和新流程，提高不同任务场景下的可用性。

核心概括：高可用的 agent 要能持续推进、遇错修正、保留状态，并用真实证据闭环。

2. 低成本

低成本不是简单地少用模型，而是在保证任务质量的前提下，减少每一轮不必要的上下文、工具和计算开销。Claude Code 的上下文工程、prompt caching 和按需扩展，本质上都是为了让长会话在成本和延迟上可持续。

📦 默认上下文轻量化

不把所有工具、规则、知识都塞进默认上下文，基础 prompt 越小，每一轮调用的固定成本越低。

🔌 能力按需加载

基础能力常驻，专业能力通过 skills、MCP、subagents、plugins 在需要时加载，避免低频能力长期占用上下文。

⚡ 重复上下文可缓存

通过 prompt caching 复用稳定前缀，让长会话中重复出现的系统规则、工具定义和项目说明不必反复支付完整成本。

🗜️ 长历史可压缩

用 /compact 等机制把冗长历史压缩成任务摘要，保留决策所需信息，清理低价值过程细节。

🔒 探索成本隔离

大规模搜索、并行调查和独立评审交给 subagent，主会话只接收结论，避免主上下文被大量中间信息拖慢。

🧹 常驻知识少而稳定

CLAUDE.md 适合放长期规则和高频约定，不适合塞大量临时资料，这既降低 token 成本，也提高缓存命中率。

核心概括：低成本的 agent 不是少做事，而是只在必要时加载必要信息，并复用稳定上下文。

3. 安全确定

安全确定意味着 agent 可以执行真实动作，但动作边界、审批规则、可回滚能力和审计记录必须由系统保证。越是能改文件、跑命令、连外部系统的 agent，越不能只依赖模型“自觉”。

🛡️ 权限分层

低风险动作自动执行，中风险动作请求确认，高风险动作禁止或进入审批流，让授权成本和动作风险匹配。

🔐 沙箱与访问边界

限制 agent 能访问哪些目录、能运行哪些命令、能连接哪些外部服务，避免一次错误决策扩大影响面。

⚙️ 硬规则系统化

安全、合规、审批、格式校验等确定性约束通过 hooks、permissions、settings、schema 校验强制执行。

💾 可回滚

修改前创建 checkpoint，出错后可以恢复现场，让 agent 的行动具备工程上的可逆性。

🧑‍💻 人类保留最终控制权

用户可以审阅计划、批准动作、暂停、回滚、恢复或分叉会话，agent 的自治必须服务于人的目标。

📜 行为可审计

工具调用、权限决策、文件修改和验证结果都应被记录，方便追踪问题和复盘 agent 的执行路径。

核心概括：安全确定的 agent 把不可妥协的规则放进系统层，用权限、沙箱、回滚和审计约束模型行动。

Claude Code 如何工作

Claude Code 的核心循环是：

  1. Gather context：读取文件、搜索代码、理解 git 状态、查看错误输出和项目说明。
  2. Take action：编辑文件、创建文件、运行命令、调用工具、启动服务或执行测试。
  3. Verify results：运行测试、检查类型错误、查看命令输出、修正前一步的结果。

这个循环不是固定流程，而是动态迭代。简单问答可能只需要收集上下文；修 bug 会在"读代码 → 修改 → 测试 → 再修改"之间循环；大型重构则会大量依赖验证。

Claude Code 本质上是 Claude 模型外面的 agentic harness。模型负责推理和决策，Claude Code 提供工具、权限、文件系统访问、上下文管理和执行环境。

内置能力

Claude Code 的工具大致分为几类：

类型 能做什么
文件操作 读文件、编辑代码、新建文件、重命名和整理文件
搜索 按模式找文件、用正则搜索内容、探索代码库
执行 运行 shell 命令、测试、构建、git、脚本
Web 搜索网页、读取文档、查错误信息
代码智能 通过语言服务器查看类型错误、跳转定义、查引用

因此 Claude Code 和只看当前文件的代码助手不同。它可以看到整个项目，跨文件理解调用关系，做协调式修改，并在修改后运行测试验证。

Claude Code 能访问什么

在某个目录运行 claude 后，它通常可以访问：

  • 当前项目目录和子目录中的文件。
  • 你能在终端里运行的命令。
  • 当前 git 分支、未提交变更和近期提交历史。
  • CLAUDE.md 中的项目说明、约定、构建命令和偏好。
  • 自动记忆 MEMORY.md，通常加载前 200 行或 25KB。
  • 你配置的 MCP、skills、subagents、Chrome 等扩展。

会话本身会保存在 ~/.claude/projects/ 下的 JSONL 文件中。每次文件编辑前也会创建 checkpoint，便于回滚。

执行环境和界面

Claude Code 的能力可以运行在多个执行环境：

环境 代码在哪里运行 适合场景
Local 本机 默认方式，能访问本地文件、工具和环境
Cloud Anthropic 管理的 VM 异步任务、远程仓库、本地没有环境时
Remote Control 代码仍在本机，浏览器远程控制 用网页界面操作本地会话

界面可以是终端、桌面应用、VS Code、JetBrains、claude.ai/code、Slack、CI/CD 等。界面不同，但底层 agentic loop 一致。

会话、分支和上下文

Claude Code 的每个会话都有独立上下文窗口。新会话不会自动继承之前的对话历史，但可以通过 CLAUDE.md 和自动记忆继承项目知识。

常见会话操作：

  • claude --continue 或 claude --resume：继续已有 session。
  • --fork-session 或 /branch：复制当前历史，创建新 session。
  • /resume：从当前 worktree 或项目中挑选历史 session。
  • git worktree：适合并行跑多个 Claude 会话，避免文件互相冲突。

切换 git 分支后，Claude 会看到新分支的文件，但当前会话历史仍保留。

权限和安全

Claude Code 有两层安全机制：

  1. Checkpoints：每次编辑前保存文件快照，可以用 Esc 两次或让 Claude 回滚。
  2. Permissions：控制 Claude 是否可以直接编辑文件或执行命令。

常见权限模式：

模式 含义
Default 编辑文件和运行 shell 命令前询问
Auto-accept edits 自动接受文件编辑和常见文件命令，其他命令仍询问
Plan mode 只读分析，先产出计划，审批后再执行
Auto mode 用后台安全检查自动评估动作，仍是研究预览能力

可以在 .claude/settings.json 中允许特定安全命令，减少重复确认。

扩展 Claude Code

Claude Code 的扩展层用于定制 Claude 知道什么、能连接什么、以及哪些流程可以自动化。

功能 作用 适合什么时候用
CLAUDE.md 每次会话自动加载的持久上下文 项目约定、构建命令、总是要遵守的规则
Skills 可复用知识、说明和工作流 部署流程、代码审查清单、API 文档、团队 playbook
Code intelligence 接入语言服务器 大型 typed codebase、需要跳转定义或看类型错误
MCP 连接外部服务和工具 数据库、Slack、浏览器、内部系统
Subagents 独立上下文里的子任务执行者 大量搜索、并行研究、避免污染主上下文
Agent teams 多个独立 Claude 会话协同 复杂并行研究、多角色评审、较大功能开发
Hooks 在生命周期事件上自动运行脚本、HTTP、prompt 或 subagent 每次编辑后 lint、阻止危险命令、发通知
Plugins 打包 skills、hooks、subagents、MCP 跨仓库复用或分发给团队

实用判断：

  • Claude 总是忘记某个约定：放进 CLAUDE.md。
  • 你总是重复输入同一个任务提示：做成 skill。
  • 你经常复制外部系统里的数据：接 MCP。
  • 一个支线任务会读很多文件：交给 subagent。
  • 某个动作必须每次都发生：写 hook。
  • 多个仓库都需要同一套配置：打包成 plugin。

类似功能的区别

CLAUDE.md vs Skill

CLAUDE.md 是 always-on，每次会话都会进入上下文，适合"Claude 永远应该知道"的规则。Skill 是 on-demand，适合偶尔使用的知识或可触发工作流。文档建议让 CLAUDE.md 保持精简，最好低于 200 行，长参考资料迁移到 skills 或 rules。

Skill vs Subagent

Skill 是"知识和流程"，会进入当前上下文。Subagent 是"隔离工作者"，有自己的上下文，只把总结返回主会话。需要复用知识时用 skill；需要隔离大规模阅读、并行任务或保持主上下文干净时用 subagent。

MCP vs Skill

MCP 提供外部工具和数据访问，Skill 教 Claude 如何正确使用这些工具。比如 MCP 连接数据库，Skill 说明数据模型、常用查询模式和团队约定。

Hook vs Skill

Hook 是确定性自动化，事件发生就执行。Skill 是给 Claude 读的指令，需要模型理解和应用。如果规则必须强制执行，例如禁止编辑 .env，应使用 PreToolUse hook，而不是只写在提示词里。

上下文窗口如何填满

Claude Code 的 context window 保存 Claude 当前能看到的一切：

  • 系统提示词和工具定义。
  • 环境信息，例如工作目录、shell、OS、git 状态。
  • CLAUDE.md、auto memory、rules。
  • 可用 skills 的描述。
  • 你的消息、Claude 的回复。
  • Claude 读过的文件内容。
  • 命令输出、测试输出、hook 返回的额外上下文。
  • subagent 返回的总结。

一个典型会话里，上下文在你输入第一句话前已经加载了一些内容：系统提示词、auto memory、环境信息、MCP 工具名、skill 描述、全局和项目 CLAUDE.md。之后每次读文件、运行命令、触发 rule 或 hook，都会继续增加上下文。

文件读取通常是上下文消耗大户。提示越具体，Claude 需要读取的文件越少。大量探索任务适合交给 subagent，因为 subagent 读过的文件不会进入主会话，只返回总结。

Compaction 之后什么会保留

当上下文快满时，Claude Code 会自动压缩，或你可以手动运行 /compact。压缩会把对话历史替换成结构化摘要。

压缩后不同内容的命运：

机制 压缩后
系统提示词和 output style 不变
项目根 CLAUDE.md 和无作用域 rules 从磁盘重新注入
Auto memory 从磁盘重新注入
带 paths: 的 rules 丢失，直到再次读取匹配文件
子目录中的 nested CLAUDE.md 丢失，直到读取该目录下文件
已调用的 skill 内容 会重新注入，但有每个 skill 5,000 tokens、总计 25,000 tokens 的限制
Hooks 不作为上下文保存，触发时才运行

如果某条规则必须跨压缩持续存在，应放到项目根 CLAUDE.md 或无作用域 rule 中。

Prompt caching 的核心机制

Claude Code 每次请求模型时都会重新发送完整上下文。Prompt caching 通过缓存"请求开头相同的前缀"来避免重复处理。

关键点：

  • 缓存匹配的是 prefix，必须精确一致。
  • 新消息通常追加在末尾，所以大部分前缀可以 cache hit。
  • 一旦前缀中靠前的内容变化，后面都要重新处理。
  • 没有"按文件"或"按片段"的独立缓存。

Claude Code 为了提高命中率，会把不常变化的内容放前面：

层级 内容 常见变化时机
System prompt 核心指令、工具定义、output style MCP 连接变化、Claude Code 升级
Project context CLAUDE.md、auto memory、无作用域 rules 会话开始、/clear、/compact 后重载
Conversation 消息、回复、工具结果 每一轮都会追加

会让缓存失效的动作

这些操作会导致下一轮部分或全部 cache miss，通常会更慢、更贵：

  • 切换模型，例如用 /model。
  • 修改 effort level，例如用 /effort。
  • MCP server 连接、断开、重连或动态更新工具列表。
  • 添加或移除整个工具的 deny rule，例如禁用 Bash。
  • /compact 替换会话历史。
  • 升级 Claude Code，因为系统提示词或工具定义可能变化。

实践建议：模型、effort、MCP server 尽量在会话开头确定；/compact 尽量放在任务自然分界处。

不会破坏缓存的动作

这些动作通常不会改变已有前缀：

  • 编辑仓库里的文件。文件内容只有被 Claude 读取时才进入上下文，编辑不会回改历史。
  • 会话中编辑 CLAUDE.md。它不会让缓存失效，但也不会立刻生效；下次 /clear、/compact 或重启才加载。
  • 修改 output style。不会立刻生效，需下次 /clear 或重启。
  • 切换权限模式。例外是 opusplan 在 plan/execution 之间切模型。
  • 调用 skills 或 commands。它们作为新消息追加。
  • /recap。它追加摘要显示，不替换历史。
  • /rewind。它回到之前已有的前缀，反而通常能命中旧缓存。
  • 启动 subagent。subagent 有自己的缓存，父会话缓存不受影响。

缓存生命周期和范围

缓存是服务端的，位置取决于你如何认证：

  • Claude subscription、API key、Claude Platform on AWS：通常在 Anthropic 基础设施中。
  • Bedrock 或 Vertex AI：在对应云服务商的模型服务基础设施中。
  • 自定义 ANTHROPIC_BASE_URL 或 LLM gateway：取决于网关如何转发和支持缓存。

TTL 方面：

🕐 Claude subscription 默认使用 1 小时 TTL。

🕐 API key、Bedrock、Vertex、Foundry、Claude Platform on AWS 默认使用 5 分钟 TTL。

🕐 可用 ENABLE_PROMPT_CACHING_1H=1 开启 1 小时 TTL。

🕐 可用 FORCE_PROMPT_CACHING_5M=1 强制 5 分钟 TTL。

在 Claude Code 中，缓存实际上接近"同一机器 + 同一目录"范围。工作目录、平台、shell、OS、auto-memory 路径、git 状态都会影响前缀。不同 worktree 通常不会共享缓存；同一目录里的并行 session 更可能共享。

如何观察缓存效果

API 返回里有两个关键指标：

字段 含义
cache_creation_input_tokens 本轮写入缓存的 token 数
cache_read_input_tokens 本轮从缓存读取的 token 数

读缓存 token 很高、写缓存 token 较低，说明缓存工作良好。如果每轮都在大量写缓存，通常意味着系统提示词、工具定义、模型、effort 或项目上下文在不断变化。

实践建议

  • 把长期规则写进 CLAUDE.md，不要依赖早期聊天记录。
  • 保持 CLAUDE.md 精简，长文档和流程迁移到 skills。
  • 对大型搜索、阅读很多文件的任务，使用 subagent 隔离上下文。
  • 对必须强制执行的规则，用 hook，而不是只写提示。
  • 需要外部系统数据或动作时用 MCP，再用 skill 补充"如何正确使用"。
  • 用 /context 检查实际上下文占用，用 /memory 检查加载了哪些记忆文件。
  • 模型、effort、MCP 连接尽量在会话开始时固定，减少中途 cache miss。
  • 在任务边界手动 /compact，不要等自动压缩打断复杂任务。
  • 如果想彻底放弃一条探索路径，优先考虑 /rewind，它比 /compact 更容易复用已有缓存。

核心理解

Claude Code 的关键设计可以概括为三层：

  1. Agentic loop：让模型能反复"理解 → 行动 → 验证"。
  2. Context engineering：通过 CLAUDE.md、skills、rules、subagents、hooks 控制什么进入上下文、何时进入、是否隔离。
